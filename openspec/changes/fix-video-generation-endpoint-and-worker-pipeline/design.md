## Context

1Dragon API와 웹이 현재 분리되어 있으나, 현재 실행 경로에서 핵심 동선이 끊겨 있습니다.
- API 런타임은 `export default { port, fetch: app.fetch }` 형태로 노출되어 실제 서버 바인딩 책임이 빌드/실행 환경에 의존합니다.
- 영상 생성 플로우는 분석/공유 라우트는 존재하지만 실제 생성 요청 라우트와 큐 적재가 연결되지 않았습니다.
- 프런트는 생성 진행을 가상 타이머로 처리해, 사용자 화면 상태가 실제 백엔드 작업 상태와 일치하지 않습니다.
- BullMQ Worker/Queue 정의는 존재하나 enqueue와 시작점 연결이 없어 상태 정합성이 깨져 있습니다.

이 변경은 단순 구현이 아니라 **실행 경로 정합성 복구**가 핵심입니다.

## Goals / Non-Goals

**Goals:**
- API 서버가 개발/운영에서 항상 HTTP 요청을 받을 수 있는 방식으로 기동되도록 정규화한다.
- `/health`를 통해 서비스 상태를 빠르게 판별할 수 있는 최소 실행 경로를 확보한다.
- 인증된 사용자 요청을 기반으로 생성 작업을 큐에 적재하고, Worker가 실제로 작업을 처리하도록 연결한다.
- 생성 요청 ID 기준으로 상태 조회와 이벤트 스트리밍(및 기존 폴링 폴백)을 일관되게 동작시킨다.
- 웹 생성 UI가 데모 타이머가 아닌 실제 API 응답/상태 이벤트를 바탕으로 동작한다.
- 실패 시 에러 메시지, 재시도 후보, 상태 전환이 사용자에게 추적 가능해야 한다.

**Non-Goals:**
- UI/브랜드 디자인 개편
- 새 AI 모델 도입, 품질 모델링 변경, FFmpeg 파라미터 튜닝
- 운영 계정 권한/요금제 정책의 근본적 변경(필요 시 기존 정책의 동작 보정은 범위 안)
- 외부 제공자(Runway/Claude/기타) SDK 교체

## Decisions

### Decision 1: API 실행 진입점은 단일 Node HTTP 인입 지점으로 고정
- **선택:** `main.ts`에서 `listen`/runtime 서버 래퍼로 실제 바인딩 수행 + 기존 `app.fetch`는 내부 핸들러로 유지.
- **이유:** 현재 `fetch` 노출 상태만으로는 실행 환경별 동작 보장성이 낮고, 운영/테스트에서 헬스체크 확인이 어렵습니다.
- **대안(미선택):** Vercel/Edge 스타일로 `fetch` 전용 배포 모드 유지
  - 이유: 현재 로컬/백엔드 Worker 구조(BullMQ + Redis + PostgreSQL)가 붙어 있어 풀 스택 상태검증과 정합성이 떨어짐.

### Decision 2: 생성 요청 API는 `/api/v1/media/jobs`(또는 기존 하위 경로 정합) 기준으로 단일 엔트리로 통일
- **선택:** 인증/요청 검증 후 `mediaJobs` 레코드 생성 또는 기존 job schema 기반 payload 저장 후 `media:generate` 큐에 enqueue.
- **이유:** 프런트에서 진행 중인 작업 상태를 Poll/SSE로 추적하려면 요청 ID가 단일 소스여야 하며, 재시도 가능해야 합니다.
- **대안:** 프런트 상태만으로 임시 진행 UI 제공
  - 이유: 실제 처리 정합성 없음, 디버깅/운영성이 낮음.

### Decision 3: 이벤트는 Outbox + SSE를 기본, 폴링은 폴백으로 유지
- **선택:** 기존 `jobEvents`/`sseBroker`/`use-job-stream` 경로를 유지하고, `/jobs/stream` 연결 실패시 `/jobs/:jobId` 폴링으로 복구.
- **이유:** SSE 미지원 환경/중간 네트워크 문제에서도 가용성 확보.
- **대안:** Polling 전용 전환
  - 이유: 즉시성/효율성 감소, 과도한 읽기 부하 가능.

### Decision 4: Worker 시작/종료 책임은 `main.ts`의 lifecycle에 통합
- **선택:** 프로세스 기동 시 worker를 생성하고, 종료 시 정상 종료하도록 정리 루틴 등록.
- **이유:** 현재 워커 생성 경로가 없어서 queue 작업 처리 자체가 실행되지 않습니다.
- **대안:** 별도 worker 실행 프로세스만 관리
  - 이유: 배포와 운영에서 프로세스 관리가 분산되어 모니터링과 롤링의 복잡성 상승.

## Risks / Trade-offs

- [Risk] `main.ts`가 동시에 HTTP 서버와 Worker를 담당하면 자원 사용이 증가한다. → **Mitigation:** 추후 분리 배포 옵션(별도 worker 프로세스)으로 단계적 분리할 수 있도록 포인트(엔트리 파일/DI 구성) 분리.
- [Risk] 큐 enqueue 전후 상태 race condition으로 `QUEUED` 조회 시점 불일치 가능. → **Mitigation:** job 생성/상태 기록을 동일 트랜잭션 경로 또는 원자성 있는 write-sequencing으로 정렬하고 최초 폴링 응답에서 `NOT_FOUND`를 적절히 처리.
- [Risk] 서버 기동 실패 시 Redis/DB 미연결 원인 구분이 어려움. → **Mitigation:** 기동 로그와 /health에서 구성요소 점검 상태(ready/connecting) 최소화해서 노출.
- [Risk] 기존 mock 데이터 UI가 실제 API로 바뀌며 QA 플로우가 실패할 수 있음. → **Mitigation:** 기능 토글 또는 단계적 배포(분석 경로 우선, 생성 경로 뒤집기)로 롤백 경로 확보.

## Migration Plan

1. 로컬/스테이징에서 `proposal` 반영 API 기동 방식 선 적용 후 `/health` 응답 확인.
2. 생성 API→큐→worker 연결을 추가하고, 큐 적재/처리 로그/상태 업데이트를 확인한 뒤 `/api/v1/media/jobs/:jobId` 조회 검증.
3. SSE + 폴링 폴백이 모두 작동하는지 대기열 이벤트로 검증.
4. 프런트 생성 흐름을 API 호출 기반으로 전환하고 데모 타이머를 제거.
5. 장애 시나리오(Redis 다운/키워드 유효성 실패/큐 미가동)에서 실패 메시지와 상태값이 안정적으로 내려오는지 확인.
6. 실패 시 롤백: 변경된 라우트/worker 기동 부분만 되돌리고 UI는 이전 동작 유지.
