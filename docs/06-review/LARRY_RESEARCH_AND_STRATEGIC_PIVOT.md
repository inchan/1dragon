## Phase 1: 리서치 — Larry 에이전트 핵심 분석

### 1.1 Larry란 무엇인가?

Ollie Warren이 만든 **OpenClaw 기반 AI 에이전트**로, TikTok 슬라이드쇼 콘텐츠를 자율적으로 생성·게시·학습하는 시스템.

| 항목 | 상세 |
|------|------|
| **결과** | 1주일 만에 800만 뷰, 월 $670 MRR |
| **인간 작업** | 하루 60초 (음악 추가 + 게시 버튼) |
| **에이전트 작업** | 15-30분 (이미지 생성, 캡션 작성, 초안 업로드, 성과 분석) |
| **게시 빈도** | 하루 3건 (앱당) |
| **성과율** | 4건 중 1건이 5만+ 뷰 돌파 |

### 1.2 Larry 아키텍처 (핵심 구조)

```
[AI 에이전트] ─── 훅 선택/생성
     │
     ├── 이미지 생성 (OpenAI gpt-image-1.5, 6장 1024x1536)
     │   └── 아키텍처(장면) 고정 + 스타일만 변경 = 일관성
     │
     ├── 텍스트 오버레이 (슬라이드 1에 훅, 세이프존 규칙)
     │
     ├── 캡션 작성 (스토리텔링, 광고 아님)
     │
     ├── Postiz API → TikTok 초안 업로드
     │
     ├── [인간] 트렌딩 사운드 추가 → 게시 (60초)
     │
     └── 성과 추적 + 자기 개선
         ├── TikTok 분석 (Postiz API)
         ├── RevenueCat (수익 추적)
         └── 스킬 파일 자동 업데이트 (50줄 → 500줄+)
```

### 1.3 Larry의 핵심 혁신 포인트

#### A. 슬라이드쇼 > 영상 (2026년 TikTok 알고리즘)

TikTok 자체 데이터:
- 사진 캐러셀: 댓글 **2.9배**, 좋아요 **1.9배**, 공유 **2.6배** (영상 대비)
- 2026년 알고리즘이 슬라이드쇼를 적극 밀어줌
- AI 이미지 생성은 해결된 문제 → 영상보다 진입장벽 극히 낮음

#### B. 자기 개선 피드백 루프 (복리 효과)

```
게시 → 성과 측정 → 패턴 분석 → 스킬 파일 업데이트 → 더 나은 게시
         │                                                    │
         └────────────── 복리 효과 (매일 더 나아짐) ──────────┘
```

- 1주차: 수백~수천 뷰 (학습기)
- 2-3주차: 1만-5만 뷰 돌파 게시물 등장
- 2개월+: 꾸준히 5만-10만+ 뷰, 수익 전환 시작

#### C. 풀퍼널 비즈니스 어드바이저 (조회수가 아닌 수익 최적화)

| 시나리오 | 진단 | 액션 |
|---------|------|------|
| 높은 뷰 + 높은 전환 | 성공 | 해당 훅의 변형 3개 자동 생성, 스케일업 |
| 높은 뷰 + 전환 없음 | CTA 문제 | 다른 CTA로 교체, A/B 추적 |
| 낮은 뷰 + 높은 전환 | 훅 문제 | CTA 유지, 더 강한 훅 테스트 |
| 낮은 뷰 + 전환 없음 | 전면 실패 | 완전히 버리고 새 접근 |
| 뷰+다운로드 많지만 유료전환 없음 | 앱 문제 | 콘텐츠 중단, 온보딩/페이월 수정 권고 |

#### D. 실용적 디테일 (시행착오로 축적)

- **텍스트 위치**: 상단 30% (상단 10%는 상태바, 하단 20%는 TikTok UI에 가림)
- **폰트 크기**: 이미지 높이의 6.5%
- **줄바꿈**: 4-6단어마다 수동 줄바꿈
- **훅**: 반드시 슬라이드 1에 전부 (절대 분할 금지)
- **6슬라이드 구조**: 훅 → 문제 → 발견 → 변환1 → 변환2 → CTA
- **캡션**: 스토리텔링 ("이거 써봤는데 솔직히 별 기대 안 했는데 이것 좀 봐요")
- **해시태그**: 최대 5개

## Phase 2: 기획 — 1Dragon 목표·목적 재정의

### 2.1 현재 1Dragon vs Larry 모델 갭 분석

| 차원 | 현재 1Dragon | Larry 모델 | 갭 수준 |
|------|-------------|-----------|---------|
| **콘텐츠 형태** | 영상 (15-30초) | 슬라이드쇼 (6장 사진 캐러셀) | **Critical** — TikTok 알고리즘이 슬라이드쇼 선호 |
| **생성 비용** | $0.93/건 (I2V 영상) | ~$0.50/건 (이미지 6장) | **High** — 비용 46% 절감 가능 |
| **생성 시간** | 60-90초 | 15-30분 (배치) | 영상이 더 빠르지만, 슬라이드쇼는 배치 가능 |
| **게시 자동화** | 미구현 | Postiz API 초안 → 수동 음악 추가 → 게시 | **Critical** |
| **성과 추적** | 미구현 | TikTok 분석 + RevenueCat 풀퍼널 | **Critical** |
| **자기 개선** | 없음 | 스킬 파일 자동 업데이트 (복리 효과) | **Critical** |
| **훅 최적화** | 카피라이팅 자동 생성 (1회성) | 성과 기반 훅 A/B → 승리 공식 축적 | **High** |
| **플랫폼** | TikTok/Shorts/Reels 동시 | TikTok 집중 | 1Dragon 우위 |
| **멀티플랫폼 변형** | 구현됨 | 단일 플랫폼 | 1Dragon 우위 |

### 2.2 전략적 판단: 영상 + 슬라이드쇼 하이브리드

**결론: 영상 파이프라인을 버리지 않되, 슬라이드쇼 생성 + 자율 게시 + 피드백 루프를 핵심 차별화로 추가한다.**

이유:
1. TikTok이 2026년 슬라이드쇼를 밀어주는 것은 **검증된 사실** (TikTok 자체 데이터)
2. 슬라이드쇼는 영상 대비 **비용 46% 저렴**, **품질 일관성 높음** (이미지 생성은 해결된 문제)
3. 영상은 여전히 Shorts/Reels에서 유효 → 멀티플랫폼 전략에 영상 유지
4. **핵심 차별화**: Larry는 단일 제품만 가능하지만, 1Dragon는 **다수 상품을 URL 리스트로 배치 처리** 가능

### 2.3 새로운 목표·목적 정의

#### 목적 (Why)
> 이커머스 셀러가 상품 URL 리스트만 제공하면, AI 에이전트가 자율적으로 멀티 플랫폼(TikTok/Shorts/Reels) 콘텐츠를 **매일 3건씩 생성·게시하고, 성과를 추적·학습하여 매일 더 나은 콘텐츠를 만드는** 자기 개선형 마케팅 시스템을 구축한다.

#### 목표 (What/Success)

| # | 목표 | 성공 기준 | 근거 |
|---|------|----------|------|
| G1 | **슬라이드쇼 + 영상 하이브리드 생성** | 상품 1개당 슬라이드쇼 1건 + 영상 1건 동시 생성 | Larry: 슬라이드쇼가 TikTok에서 2.9배 효과 |
| G2 | **하루 3건 자동 발행** | 상품 URL 리스트 → 하루 3건 초안 자동 생성, 플랫폼별 최적화 | Larry: 볼륨이 완벽함을 이긴다 |
| G3 | **성과 기반 자기 개선 루프** | 게시물 성과 추적 → 훅/CTA 패턴 분석 → 다음 생성에 반영 | Larry: 스킬 파일 50줄→500줄 복리 효과 |
| G4 | **풀퍼널 비즈니스 피드백** | 조회수→클릭→전환 추적, 카테고리별 KPI 자동 리포트 | Larry: "대부분 도구는 뭐가 일어났는지, Larry는 뭘 고쳐야 하는지" |
| G5 | **원가 효율** | 슬라이드쇼 ≤$0.50/건, 영상 ≤$1.00/건 | Larry: gpt-image-1.5 $0.50/건, Batch API $0.25/건 |
| G6 | **2개월 내 성과 복리** | 1주차 수백뷰 → 3주차 1만+ → 8주차 5만+ 뷰 평균 | Larry 실증 데이터 |

#### 범위 (Scope)

**포함:**
- 슬라이드쇼 생성 엔진 (이미지 6장 + 텍스트 오버레이 + 캡션)
- 게시 자동화 (TikTok 초안 업로드 via Postiz 또는 자체 API)
- 성과 추적 시스템 (TikTok/Instagram/YouTube 분석 수집)
- 자기 개선 피드백 루프 (훅 성과 패턴 → 다음 생성에 반영)
- 카테고리별 KPI 대시보드
- 상품 URL 배치 크롤러

**제외 (이번 사이클):**
- 모바일 앱 (웹 전용 유지)

## Phase 2.5: 실행 워크플로우 12단계 설계

### 전체 워크플로우

```
[리서치] → [기획] → [피드백] → [재기획] → [개발] → [QA]
    → [피드백] → [코드리뷰] → [퀄리티 개발] → [QA] → [회고] → [에이전트업데이트]
```

### 단계별 산출물 정의

| # | 단계 | 담당 | 산출물 | 완료 기준 |
|---|------|------|--------|----------|
| 1 | **리서치** | 기획+데이터 | Larry 분석 보고서, 시장 갭 분석 | ✅ 본 문서 |
| 2 | **기획** | 기획 | 목표·범위 정의, PRD 초안, 기술 요구사항 | ✅ 본 문서 |
| 3 | **피드백** | CEO + 전체팀 | 기획 리뷰 의견, 우선순위 조정 | 피드백 문서 |
| 4 | **재기획** | 기획 | 피드백 반영 확정 PRD, 스프린트 계획 | 확정 PRD |
| 5 | **개발** | 개발팀 | 코드 구현 (TDD, 도메인별 분리) | 기능 단위 통과 |
| 6 | **QA (1차)** | QA팀 | 기능 테스트, 시나리오 검증 | 테스트 리포트 |
| 7 | **피드백 (2차)** | CEO + 전체팀 | QA 결과 리뷰, UX 피드백 | 보완 요구사항 |
| 8 | **코드리뷰** | 개발 시니어 | 아키텍처·보안·성능 리뷰 | 리뷰 통과 |
| 9 | **퀄리티 개발** | 개발팀 | 리뷰/QA 피드백 반영, 엣지케이스 처리 | 전체 테스트 통과 |
| 10 | **QA (2차)** | QA팀 | 리그레션 + E2E + 성능 테스트 | 릴리스 승인 |
| 11 | **회고** | 전체팀 | 회고 문서 (잘한 점, 개선점, 학습) | 회고 완료 |
| 12 | **에이전트업데이트** | 기획+개발 | 에이전트 스킬 파일 업데이트, 메모리 갱신 | 에이전트 학습 반영 |
