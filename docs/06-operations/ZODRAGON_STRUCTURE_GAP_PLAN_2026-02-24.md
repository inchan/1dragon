# Zodragon 구조 진단 및 실행 계획 (2026-02-24)

## 1) 현재 프로젝트 구조 (코드 기준)

### Monorepo 레이어
- `apps/api`: 백엔드 API, 도메인/유스케이스/인프라(Queue/Provider/DB)
- `apps/web`: 프론트엔드(FSD 기반 기능 모듈)
- `packages/shared`: 공용 enum, zod schema, 타입
- `docs`: 제품/전략/아키텍처/시뮬레이션 문서

### API 내부 계층
- `src/domain/*`: 비즈니스 엔티티/정책/포트
- `src/application/*`: 유스케이스 오케스트레이션
- `src/infrastructure/*`: BullMQ, Provider 어댑터, 저장소, 로깅
- `src/api/*`: Hono 라우트/입출력 어댑터

## 2) 분야별 현재 상태와 갭

### 개발(백엔드)
- 강점: 멀티 Provider 라우팅, 큐 기반 비동기 처리, 상태 이벤트(outbox) 기반 실시간 업데이트
- 갭(P0): 재시도·백오프·DLQ·서킷브레이커·일일 발행 헬스 기준이 타입 계약으로 충분히 잠기지 않음

### 데이터
- 강점: job/variant/event 스키마와 상태추적 축은 존재
- 갭(P1): 카테고리별 KPI 피드백 루프(성과 수집→다음 생성 정책 반영) 미완성

### 콘텐츠 파이프라인
- 강점: 스타일/카피/멀티플랫폼 변형 파이프라인 연결
- 갭(P1): URL 리스트 기반 대량 입력과 1일 3건 자동 보장 파이프라인의 운영 자동화 부족

### 운영(SRE/운영자동화)
- 강점: BullMQ + Redis + 로그 체계 기초 있음
- 갭(P0): DLQ 운영 규칙, 서킷 복구 조건, 일일 발행 헬스 경보 기준의 명시/자동화 부족

### QA(개발 관점)
- 강점: 도메인/유스케이스/워커 테스트 기반 존재
- 갭(P0): 신뢰성 정책(재시도/DLQ/서킷/헬스)에 대한 회귀 체크리스트와 테스트 케이스 표준화 부족

## 3) 목표 정렬 (ROUND GOAL 반영)

핵심 목표:
- 멀티 플랫폼
- 카테고리별 KPI 전략
- 하루 3개 발행 보장
- 상품은 특정 URL 리스트 입력
- 톤 다양
- 이미지 1장 + 카피(+추가요소)

코드 레벨 우선순위:
1. **P0 신뢰성 계약 잠금**: 재시도·백오프·DLQ·서킷·일일 3건 헬스 기준
2. **P1 URL 리스트/배치 스케줄러 본체**: 하루 3건 자동 생성/집행
3. **P1 KPI 폐루프**: 성과 수집 기반 카테고리별 정책 자동조정

## 4) 실행 계획 (자율 진행)

### Phase A (즉시, P0)
- 도메인 포트에 신뢰성 계약 타입 고정
- Queue/Router/Worker에 계약 반영
- DLQ 라우팅 구현
- 일일 발행 헬스체크 API 제공
- 운영 기준서 + QA 체크리스트 문서화

### Phase B (다음, P1)
- URL 리스트 크롤러(도메인/포트/어댑터)
- 배치 스케줄러(일 3건 기본값, 타임슬롯 정책)
- Web 운영 플래너 화면 및 API 연결

### Phase C (후속, P1~P2)
- 카테고리 KPI 수집/분석 파이프라인
- 톤/스타일 자동 추천 로직 강화
- 알림 채널(Ops) 연동과 온콜 룰 세분화

## 5) 완료 기준
- P0 계약이 코드 타입으로 명시되고 테스트가 존재할 것
- P0 운영 문서(계약/운영/QA)가 최신 코드와 일치할 것
- `typecheck` + 관련 단위 테스트가 통과할 것
